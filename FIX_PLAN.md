# План исправлений (FIX_PLAN)

Принято по итогам ревью:
- **П1–П5** (дюпы инвентаря / потеря ресурсов / гонки апгрейда и склада / stack size) — **НЕ трогаем** (решение владельца).
- **П6** (права `/tbuildings stock`) — **НЕ трогаем** (настраивается через townyperms).
- **П7–П24 + гигиена кода** — исправляем.

Рабица: каждый этап = коммит, после каждого этапа — `mvn -q clean package` (обязательная зелёная сборка). Геймплей не меняется: правки только защитные (откаты, рефанды, валидации, кэши).

---

## Этап 1 — Возврат наград при ошибках (П2, П10)
**Файлы:** `service/impl/RewardServiceImpl.java`, `service/OnlineTimeService`/`impl`, `task/HourlyRewardTask.java`

1. В цепочке выдачи награды добавить `.exceptionally(...)`: при падении депозита/сохранения **возвращать списанные часы** (рефанд online_time) и логировать ошибку.
2. При переполнении городского хранилища: overflow-часть награды не терять — либо складывать в overflow-очередь с повторной попыткой при следующем часовом тике, либо выдавать предметами в инвентарь онлайн-мэру (выберем простое: **overflow-депозит повторяется на следующем тике**, часы при этом НЕ возвращаем, т.к. награда засчитана).
3. Обернуть `thenAccept`-блоки с мутацией часов в try/catch → рефанд.

**Критерий:** ни один час не «сгорает» без записанного результата; тест: временно смоделировать исключение БД → часы остались.

## Этап 2 — Гонки и откаты GUI/апгрейда (П7, П11, П12, П17)
**Файлы:** `gui/session/PageSessionRegistry.java`, `service/impl/BuildingServiceImpl.java` (upgrade), `listener/UniversityListener.java`, `cache/TownCache.java`

1. **П12 (rollback):** порядок действий при неудачном финальном UPDATE — сначала успешный `rollbackItems` (предметы игроку/в склад), **затем** инвалидация сессий. Сейчас наоборот → предметы теряются.
2. **П11 (баланс):** перед списанием монет делать свежую проверку баланса (или повтор при `insufficient funds` после await), чтобы ложной ошибки «not enough coins» не было.
3. **П7 (выход из города):** при `invalidateTown` синхронно закрывать открытые GUI-сессии этого города (`player.closeInventory()` через scheduler), чтобы после смены тауна нельзя было действовать в старом окне.
4. **П17 (UniversityListener):** в отложенной выдаче (20 тиков) перед действием проверять, что игрок всё ещё онлайн **и** состоит в том же городе (UUID города из кэша сессии). Иначе — молча пропуск.

**Критерий:** no NPE/dup-окна; апгрейд с падающим UPDATE возвращает предметы; студент, вышедший из города, пермишен не получает.

## Этап 3 — Main-thread и lifecycle (П13, П14, П21, П24)
**Файлы:** `command/AdminCommand.java` (+handlers), `TownBuildingsPlugin.java`, `database/DatabaseManager.java`, все sweep-задачи (`PageSessionRegistry`, `BlockPlaceTracker`, `EconomyService`-кэш и др.)

1. **П13:** синхронный flush в админ-командах перевести в async с уведомлением оператора о результате (сообщения `messages.yml` уже есть).
2. **П14:** миграция БД на старте — вынести в async-поток до регистрации задач; first-run не должен ловить watchdog (задачи стартуют после готовности пула).
3. **П21:** хранить ссылки на все повторяющиеся sweep-задачи и отменять их в `onDisable` (сейчас утечка после reload).
4. **П24:** `CallerRunsPolicy` в DatabaseManager заменить на `AbortPolicy` + явная обработка `RejectedExecutionException` (лог + отказ операции, но main-тред не фризим).

**Критерий:** `/tbadmin logs` не фризит сервер при медленной БД; после `/reload` нет ошибок «plugin disabled» из scheduled tasks.

## Этап 4 — Корректность данных и слушателей (П15, П16, П9)
**Файлы:** `listener/TownListener.java`, `listener/HeadquartersStackListener.java`, `service/impl/EffectServiceImpl.java`

1. **П15:** удаление строк БД при роспуске/выходе — по **UUID города из события**, а не по имени (защита от дублей имён/переименований).
2. **П16:** перед мутацией предмета в руке — `clone()`, запись только в клон, затем `setItem`; исключаем двойную запись/мутацию оригинала.
3. **П9:** EffectService — горячий путь resident→town перевести на существующий TTL-кэш TownCache вместо прямых запросов Towny на каждое событие блока.

**Критерий:** TPS-профиль событий блоков не деградирует; данные чужого города с тем же именем не удаляются.

## Этап 5 — Оптимизации горячего пути (П18, П19, П20, П22, П23)
**Файлы:** `database/dao/StockDao.java`, `database/dao/InventoryDao.java`, `gui/menu/BranchMenu.java` (+ прочие меню), `gui/Menu.java`, `util/*`

1. **П18:** `countAll` — агрегация на уровне SQL (material→amount без полной десериализации BLOB) или in-memory агрегат, обновляемый при записи.
2. **П20:** DAO загружать только запрашиваемую страницу, а не все страницы инвентаря.
3. **П19:** BranchMenu — кэшировать собранный MiniMessage-lore на здание/уровень (инвалидация при reload конфигов), не пересобирать на каждый refresh.
4. **П22:** Menu API — реально использовать переменную `viewer` при рендере (корректный контекст имени/правки).
5. **П23:** составной ключ `uuid + "|" + townUuid` → компактный key (record/long-pair или конкатенация без аллокации String под каждый get) в самых горячих мапах.

**Критерий:** замер до/после (jfr/таймеры в логе debug): время открытия склада и refresh меню снижено; поведение идентично.

## Этап 6 — Гигиена кода (без изменения поведения)
1. Формула количества страниц — в одно место (`util` или `InventoryService`), убрать 4 дубля.
2. Таймауты EconomyService: не возвращать `0.0` как «нет денег» — отдельный результат/исключение, сообщения об ошибке корректные.
3. Удалить мёртвый код в пустых слушателях/заглушках.
4. Мелочи: final-поля, early-return, константы магических чисел (duration тиков и т.п.).
